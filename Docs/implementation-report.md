# Wina Bwangu: Implementation Report

## Introduction

In our group project, we developed Wina Bwangu as a web application for managing six transaction booths, five financial services and the customer transactions processed at each location. We built it as a client-server application using HTML, CSS and JavaScript on the frontend, Node.js and Express on the backend, and SQLite with better-sqlite3 for persistent storage. Our purpose was to replace a manual or fragmented process with a controlled workflow that supports transaction capture, reporting, user administration and operational decision-making.

## Tools and technologies used

We used semantic HTML for the dashboard, forms, tables and modal dialogs. We organised CSS into a core stylesheet and focused module files for the dashboard, cash services, login, settings, users, transactions and modals. This makes presentation changes easier for our group to maintain and prevents one large stylesheet from becoming a dependency for every page. We also split JavaScript into modules. Dedicated modules manage authentication, API calls, dashboard rendering, transaction processing, settings, users, receipts, pagination and modal behaviour. This separation follows the Single Responsibility Principle: each module has one clear reason to change.

We built the server with Express. Our routes expose authentication, booths, services, transactions and users as separate resources. Middleware performs authentication and capability checks before protected route handlers execute. We store passwords as salted hashes rather than plain text. SQLite provides relational tables for users, booths, services, booth-service assignments and transactions. Foreign keys, unique transaction references and server-side validation protect the data model.

Our application uses normal browser fetch requests to communicate with the backend. We designed the transaction form to load valid booths and services dynamically, display the selected booth location, validate phone or account details according to the service, and show a confirmation modal before processing. Successful create, update and delete operations use success feedback modals. Users can search, filter, paginate and print transactions as receipts.

We designed the database around the business rules rather than treating the interface as the source of truth. Booths and services are maintained independently, and the `booth_services` junction table records which services are available at each booth. Each transaction references both a booth and a service through foreign keys. This prevents orphaned records and makes our reports dependable. Unique constraints protect usernames, service names, booth names and transaction references. Our seed process checks the appendix references, booth/service relationships and revenue rates before inserting rows, so a data-entry error fails early instead of silently creating an inaccurate report.

## Implications of the application outputs

We designed the dashboard to convert raw transaction rows into useful management information. It displays total revenue, transaction count, active booths and the total capital required. We calculate the capital figure from the five monthly service limits, giving K740,000 for the case-study configuration. Service performance shows transaction frequency, revenue, credit used, remaining monthly capacity and a status indicator. This allows management to identify services approaching their limits before the next transaction is attempted.

We included booth performance so the dashboard shows cumulative revenue and the frequency of each service at each booth. Our service and booth pie charts communicate the relative contribution of each category at a glance, while the bar charts make exact comparisons easier. We also summarise tax obligations by service. We implemented the case-study instruction to assume 16% tax consistently: the browser previews it, but the backend recalculates tax, amount after tax and service revenue before inserting a transaction. Consequently, a modified browser request cannot change the stored financial figures.

From our analysis, the outputs have operational implications. A low-revenue booth may require marketing or a review of its service mix. A booth with high transaction frequency may need stronger cash-handling controls or additional staffing. A service with high credit utilisation may require capital planning, while the remaining-limit display provides an early warning. The transaction reference, timestamp, booth, service, customer identifier and operator session create an audit trail for reconciliation and investigation.

Our output also supports accountability between operational and management users. Agents need a focused view of the booths and services assigned to them, whereas an administrator needs the consolidated view required for planning. Filtering and pagination prevent a long activity list from becoming difficult to use, and the recent-activity display makes new transactions visible immediately after a successful save. The printable receipt provides a simple customer-facing record without exposing unrelated dashboard data. Together these features reduce ambiguity during end-of-day balancing: the operator can compare receipt references with the activity list, while management can compare booth totals with the service-level totals.

## Operational controls and security

We implemented three roles: system administrator, admin agent and agent. The system administrator can manage users, booths, services and transactions. The admin agent can view configuration and process transactions but cannot manage users or change configuration. The agent can view permitted operational data and process transactions only within assigned booths and services. The server enforces these rules independently of the interface, while the frontend hides unavailable navigation and actions to avoid confusing users.

We require confirmation for all create, update and delete actions. Our validation checks required values, numeric limits, dates, email addresses, customer contact formats and service availability. The interface prevents duplicate submission while a transaction is processing. Sessions support login and logout, and the forgot-password flow provides a controlled recovery path. Receipts can be printed for customer or operational records. Responsive layouts, fixed modal headers and footers, internal modal scrolling, hover states and reduced-motion-friendly transitions improve usability across screen sizes.

The design also considers maintainability and accessibility. Forms use labels and meaningful field names, modal dialogs expose their purpose through headings, and buttons communicate the action that will occur. The red brand colour is used consistently for primary actions and headings, while neutral surfaces preserve contrast and reduce visual noise. CSS transitions are short and purposeful, and the interface remains usable when a user prefers reduced motion. The application’s modular structure makes it possible to update a modal, a table, or a role capability without rewriting unrelated features. This is important for a financial workflow because small changes should be reviewable and testable.

## Testing and conclusion

We wrote automated tests for password hashing, shared validation, role capabilities, the 308-reference appendix dataset and the 16% transaction calculation. Our accompanying test plan covers authentication, role restrictions, dynamic form behaviour, CRUD confirmations, pagination, printing, dashboard calculations, responsiveness and recovery from invalid input. Before submission, we reseed the database with `node database\\seed.js` so it contains the 308 Appendix 1 records, and we check the application using the demo accounts documented in the test plan.

Overall, our Wina Bwangu implementation satisfies the case-study workflow while providing a modular foundation for future changes. Its main value is not only storing transactions, but turning those transactions into controlled, auditable and understandable information for daily booth operations and management planning.
